# メタモデルと検査規則の設計判断

README の[メタモデル](../../README.md#メタモデル)と[検証 (3層)](../../README.md#検証-3層)が
規則そのものを書くのに対し、ここは**なぜその規則なのか**を残す。
規則を変えるとき、同じ議論を繰り返さないための文書。

## 語尾規則を指示書より緩く取った

初回の実装指示書 (issue #1) の記述をそのまま条件式にすると実務的に破綻する箇所が
2 つあり、意図を汲んで次のように解釈した。

- **Need の語尾規則**: 指示書は「〜したい」。ただし「気づきたい」「知りたい」のような
  サ変以外の願望形を弾いてしまうため、**「〜たい」**で判定する。
- **FR の語尾規則**: 指示書は「〜すること」。同様に「読み取ること」「送ること」を弾くため、
  **「〜こと」**で判定する。

いずれも末尾の句点は許容する。厳密に「〜したい」「〜すること」に戻すなら
`src/reqmodel/model.py` の `_check_suffix` 2 か所を変えるだけでよい。

## `constrains` を `structure.status_inconsistent` の対象から外した

`structure.status_inconsistent` が見るのは `satisfies` / `refines` / `qualifies` /
`motivates` の 4 種で、**`constrains` は対象外**である (`validate.py` の `_STATUS_EDGES`)。

制約は制約対象より先に決まりうる。「MCP サーバを作るなら依存を増やさない範囲で」は
着手前に決まっているからこそ意味があり、承認済みの Constraint が proposed の要求を
指すのは成熟度の逆転ではない。制約側の status を下げれば黙るが、それは実態に反する。

これは[このリポジトリ自身の要求モデル](../../README.md#このリポジトリ自身の要求モデル-dogfooding)を
`--strict` に通す過程で見つかった誤検出である。approved な Constraint が proposed な
FR を `constrains` した結果が報告され、抑制ではなく検査そのものを直した (#47)。

## `Decision` 型と `conflicts` / `resolves` を置かない

対立の明示 (`conflicts`)、その解消の記録 (`Decision` / `resolves`)、そして
`structure.conflict_unresolved` / `structure.resolve_no_conflict` /
`structure.resolve_invalid` の 3 チェックをメタモデルから外した。決定の内容は
**要求 (FR) として書く**。

分かれ目は**決定の中身が何の形をしているか**にある。外した時点でモデルに存在した
`Decision` は 2 件で、どちらも対立する要求のどちらかを選んだのではなく、新しい
仕組みを持ち出して両立させていた (「規程照合に要する項目を既定値から自動補完する」
「選択したノードの近傍だけを描くフォーカス表示を設ける」)。主語はシステムで、
消すと機能が減る。[どの型に書くか](../../README.md#どの型に書くか-主語で決める)を
当てれば、これは FR である。

FR の中身が `Decision` に書かれていると、FR に課される規則をすべて回避する。
語尾規則がかからず、`acceptance_criteria` を持てず、`Decision` は `Sourced` では
ないので `has_source` も持てず、`structure.orphan_fr` の対象外で、
`req doc --matrix` のトレーサビリティ表にも出ない。実際 `requirements.py` では
「フォーカス表示を設けること」が FR として存在せず、この機能が現れるのは D-1 の
`text` と QR-1 の受け入れ基準 (「フォーカス 2 ホップ表示の倍率が 0.5 倍以上」) の
中だけだった。**解決策は既に片方の要求の受け入れ基準へ漏れ出しており**、
「決定は `Decision` に一元化されている」という前提は先に崩れていた。

**捨てたもの**: 「対立に気づいているが、まだ決めていない」という**開いた状態**。
FR に畳んだ後の text は決着した姿しか表さず、テキストには状態も検査も持てないので
これは復元できない。ただしこれは構造上の事実ではなく進行中のプロセスの状態であり、
「人・時点・経緯は Git、構造はモデル」という既存の分担 (README の
「Git を履歴・レビュー基盤とする」) の前者側にあたる。
決着すれば解決策が FR として残り、揉めた経緯は commit と PR が持つ。

**この判断はプロジェクトの性格に依存する。** 複数の当事者が交渉する場では、
未解決の対立を一覧に出して会議を強制すること自体に価値があり、そこでは
`conflicts` を残す意味がある。このリポジトリは書き手が 1 人で、対立が open な
まま残る期間がそもそも無いため、検査が働く余地がなかった。書き手が増えて
「決まっていないことを機械に数えさせたい」場面が出てきたら、ここを読み直して
戻す判断をしてよい。

`Decision` が `has_source` を持たない非対称は以前から気になっていた点だが、答えは
「`has_source` を足す」ではなく「`Decision` が要らない」だった。中身が FR なら
`has_source` も語尾規則も受け入れ基準も最初から付いてくる。

## Goal 層を Need の言い換えから作り直した

`requirements.py` の `Goal` を 5 件 (G-1 の下に G-2〜G-5) から **3 件の 1 層**に
畳み、本文を世界の側の記述に書き直した。`refines` による Goal の中間層は無くなった。

**何が起きていたか。** 旧 G-1「要求の構造的な誤りと変更の影響を、人手のレビューに
頼らず機械的に把握できる状態にする」は、旧 G-2 (構造上の誤り) と旧 G-3 (変更の影響) の
本文を連結しただけで、親が子を要約していなかった。しかも `decomposition="AND"` を
持ちながら旧 G-4 (LLM) と旧 G-5 (共有) は親の本文に現れず、4 子のうち 2 子だけを
言い換えた親になっていた。

子の側も同じで、旧 G-2「要求の構造上の誤りを、レビュー会を待たずに発見できる状態に
する」は N-1「要求を書く人は、書き方の誤りをレビュー会の前に自分で見つけたい」の
**主語を落として語尾を変えただけ**の同一命題である。旧 G-3 は N-3 の、旧 G-5 は N-6 の
言い換えで、旧 G-4 は主語がシステムだった。

原因は規則の非対称にある。`Need` の「〜たい」は層1 のエラーだが、**`Goal` には本文の
規則が一つも無い**。`Need` をコピーして「〜できる状態にする」に変えた文が素通りする。

**荷重を負っていないことは実測できる。** 旧 G-2〜G-5 を消して 8 つの `Need` を旧 G-1 に
直付けしたモデル (55 ノード / 120 エッジ → 51 / 110) は `--strict` で指摘ゼロのまま
通る。`structure.goal_leaf` も `structure.goal_decomposition` も、Goal が `motivates` を
1 本でも持てば満たされるためで、中間層は検査に何も足していなかった。

**書き直しの基準**は[どの型に書くか](../../README.md#どの型に書くか-主語で決める)の
主語の規則、すなわち **`Goal` は解決策が無くても成り立つ世界の側の変化**である。
reqmodel が存在しなくても述べられる文になっているかを条件にすると、8 つの `Need` は
3 つの束に落ちた。

| | 本文 | motivates |
|---|---|---|
| G-1 | 要求の不備が後工程で見つかることによる手戻りを減らす | N-1, N-2, N-8 |
| G-2 | 要求を変えるたびに繰り返される影響調査の負荷を減らす | N-3, N-4 |
| G-3 | 要求の理解が書き手に依存する度合いを下げる | N-5, N-6, N-7 |

**捨てたもの**: Goal どうしの階層 (`refines`) が `requirements.py` から無くなり、
図と `req doc` の要求階層は Goal → Need の 2 段で始まる。`decomposition` 属性も
このモデルでは表示されない (子から `refines` されている Goal にしか意味が無いため)。
どちらもメタモデルからは消しておらず、束ねる中間目標が実際に要るときに戻せる。
ここで畳んだのは**中間層が言い換えでしか埋まっていなかった**からで、階層そのものを
否定したのではない。

**再発は機械では止められていない。** `Goal` の本文規則 (役割主語を書かない・
「〜たい」で終わらない・`motivates` 先の言い換えにしない) は文書にしか無く、
`req validate` は今も何も言わない。同じ崩れは次も素通りする。

## 型を分ける基準

**型ごとに異なる構造規則が存在するときだけ型を分ける**。

- FR と QR は分ける。`qualifies` を出せるのは QR のみで、孤立検出の規則も異なる
- `Source` は単一型とし、`kind: "stakeholder" | "document" | "existing_system"` で
  分類する。3 種の構造的振る舞いが同一のため。将来 Stakeholder 固有のエッジが
  必要になったら `Stakeholder(Source)` としてサブクラス化すればよく、エッジ型定義は
  `Ref[Source]` のまま無傷
- 引用 (規程の条文、ヒアリングでの発言) も `Source` とし、`part_of` で親にぶら下げる。
  引用も「要求から参照される」「要求を持たない」という点で振る舞いが同じで、`part_of`
  の有無は Goal の `refines` と同じ同一型内階層にすぎない

## 引用を Source のノードにする

引用文の置き場所には 2 つの案があった。

1. **エッジに載せる** — `has_source=[(src_policy, "第12条第3項…")]`
2. **ノードにする** — 引用を `Source` として書き、`part_of` で親にぶら下げる

採ったのは 2 である。分かれ目は**引用に同一性があるかどうか**にある。

1 では、同じ条文を N-2 と FR-3 と C-1 が引くと引用文が 3 か所に重複し、しかもそれが
同じ条文であることを機械的に判定できない (ただの文字列なので表記が 1 文字違えば別物
になる)。「この源泉のどこが使われているか」を集約する用途と正面から衝突する。
2 では引用が id を持つので、3 つの要求が同じ引用ノードを指し、集約が構造から出る。

実装上の差も大きい。`Edge` は `source` / `name` / `target` の 3 フィールドで、`Ref` も
id 文字列に潰れる。エッジ属性の導入は `_analyze()`・グラフ構築・正規化 JSON・`plan` の
構造 diff・`doc`・`site` に波及する。2 はメタモデルの骨格に触らずに済む。

**捨てたもの**: 同じ引用を要求ごとに違う意図で読んだ場合、その差は表現できない。
引用ノードは 1 つに集約されるので、読みの差は要求側の `text` に落ちる。読みごとに引用を
分けると同一性が壊れ、集約の利点を失う。集約を取ってこちらを捨てている。

## Source を図に描かない

`Source` はノード型として残しつつ、**図には描かない**ことにした
(`model.SOURCE_EDGES`)。`req graph` / `req explain` / 静的サイトの図のいずれも既定で
源泉を落とし、源泉は参照元ノードの属性として出す。`--with-sources` で従来の描画に
戻せる。

分かれ目は**源泉が経路なのか属性なのか**にある。`refines` や `satisfies` は「この要求
はどの要求と繋がっているか」を辿るための経路で、図はそれを読むためにある。源泉は
違う。「この要求はどこから来たか」はノード 1 件について読む情報で、他の要求へ渡って
いくための経路ではない。経路でないものを経路として描いていた。

数がそれを裏書きする。`requirements.py` は `Source` 6 件に対し `has_source` が 60 本
あり、**全エッジ 116 本の過半が源泉**だった (図に残るのは 56 本)。1 件の Source が
平均 10 件の要求から参照されるハブなので、レイアウトが源泉に引っ張られて要求どうしの
関係が読めなくなる。
README も以前から「深さ 2 以上では `has_source` を外すとよい」と、手で外す運用を
勧めていた。既定を実態に合わせたことになる。

`req doc` は最初から `- 源泉: SRC-EMP (申請者となる一般社員)` と属性として出しており、
図の側だけが取り残されていた。今回は新しい方針の導入ではなく、既存の扱いへの
一貫化である。

**型は変えていない。** `has_source` / `part_of` フィールド、`structure.missing_source`
/ `structure.unused_source` / `structure.part_of_cycle`、源泉トレース率、
`Source × 要求` 表はすべてそのまま。変わるのは描画だけで、検査は無関係である。

**捨てたもの**: 図の上で Source をクリックし、その条文に依存する要求を一斉に光らせる
操作は、既定では取れなくなった。型を消さず絞り込みで戻せるようにしたのはこのため
である。集約して見る用途は `req doc` の源泉節・`Source × 要求` 表・テーブルビューが
引き続き担う。
